# Phase 146.1: Resync Section-Identity Fix - Context

**Gathered:** 2026-06-23
**Status:** Ready for planning
**Mode:** Gap closure (v0.7.0 milestone audit — LINK-01 / INTG-05 blockers)

<domain>
## Phase Boundary

Close the two cross-phase blockers found by the v0.7.0 milestone audit
(`.planning/v0.7.0-MILESTONE-AUDIT.md`). Both share **one root cause**: the
`recipe_sections.technique_section_id` column (added by migration 052 for the
live-link resync's exact section identity) is **never written by the production
apply path**, so the resync match map is always empty and every technique
edit+save INSERTs duplicate sections instead of updating the originals.

Three production write-sites must populate / carry `technique_section_id`:
1. `applyTechnique` (`src/db/queries/recipeTechniqueInstances.ts`) — the
   `INSERT INTO recipe_sections` must include `technique_section_id` set to the
   source `technique_sections.id` (the `section.id` already in scope in the loop).
2. `duplicateRecipe` (`src/db/queries/recipes.ts`) — the section-copy
   `INSERT INTO recipe_sections` must carry `technique_section_id` from the
   source section (`section.technique_section_id ?? null`).
3. `RecipeSection` type (`src/types/recipeSection.ts`) — declare
   `technique_section_id?: number | null` so the column is readable under strict TS.

A guard-first regression test must drive the **real** `applyTechnique` path
(NOT a manual UPDATE like `technique-resync.test.ts` did) → edit the technique
structurally → assert the recipe's technique section count stays stable (no
duplication) and step-completion progress survives. A second test covers
`duplicateRecipe` carrying `technique_section_id` and surviving a resync.

**Out of scope:** any new migration (052 already added the column); the
non-blocking `UNFILLED_SLOT_COUNT_KEY` invalidation warning (tech debt, tracked
separately); the v0.7.0-v2 UX backlog items.

</domain>

<decisions>
## Implementation Decisions

### Root-cause fix (one column, three sites)
- Add `technique_section_id` to `applyTechnique`'s recipe_sections INSERT —
  column list + value `section.id`. `section` is the `technique_sections` row
  already iterated in the apply loop.
- Add `technique_section_id` to `duplicateRecipe`'s recipe_sections INSERT —
  column list + value `section.technique_section_id ?? null`. The source
  `section` comes from `SELECT * FROM recipe_sections`, so the value exists at
  runtime once the type declares it.
- Add `technique_section_id?: number | null` to the `RecipeSection` interface.

### Guard-first regression (drive the REAL path)
- The new test seeds via `applyTechnique(...)` (the production function), NOT a
  manual `UPDATE recipe_sections SET technique_section_id`. This is the exact
  gap that let the original bug ship — the regression test must close it.
- Assert: after `applyTechnique` then a structural `saveTechniqueGraph` edit, the
  count of `recipe_sections WHERE technique_instance_id = ?` is unchanged (no
  duplicate set) and a previously-completed step's `unit_recipe_step_progress`
  row still exists (FND-03).
- Assert: `duplicateRecipe` copies produce sections whose `technique_section_id`
  is non-NULL and equal to the source, and a subsequent resync updates (not
  duplicates) them.

### Claude's Discretion
- Test file placement/naming under `tests/data-layer/` (e.g.
  `technique-resync-apply-path.test.ts`), mirroring existing conventions.
- Whether to extend `technique-resync.test.ts` or add a new file.

</decisions>
