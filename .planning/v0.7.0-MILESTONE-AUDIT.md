## Blocker 1 — LINK-01: resync duplicates sections instead of updating

**Root cause:** `applyTechnique` (`src/db/queries/recipeTechniqueInstances.ts:80-91`) omits `technique_section_id` from its `INSERT INTO recipe_sections`. Migration 052 added that column specifically so `resyncTechniqueInstances` can match sections by stable identity. Production-applied sections always have it NULL → the resync match map is empty → every technique edit+save INSERTs a fresh duplicate section set and orphans the originals (count doubles per save; progress markers vanish from the UI).

**Why tests didn't catch it:** `tests/data-layer/technique-resync.test.ts:133-135` manually UPDATEs `technique_section_id` after creating the section, bypassing `applyTechnique`. The data layer was proven against a fixture that doesn't match production.

**Fix (surgical):**
1. Add `technique_section_id` to the `applyTechnique` `recipe_sections` INSERT (column list + `section.id` value — already in scope in the loop).
2. Add a regression test that drives the **real** `applyTechnique` path (not a manual UPDATE), then edits the technique and asserts the section count is stable (no duplication) and progress survives.

## Blocker 2 — INTG-05: duplicated recipes inherit the break

**Root cause:** `duplicateRecipe` (`src/db/queries/recipes.ts:226`) copies `recipe_sections` without `technique_section_id`, and `RecipeSection` (`src/types/recipeSection.ts:41`) doesn't declare the field (reads back `undefined` under strict TS).

**Fix (surgical):**
1. Add `technique_section_id` to the `RecipeSection` type.
2. SELECT + copy `technique_section_id` in `duplicateRecipe`'s section INSERT.
3. Extend the duplication test to assert the copied technique sections carry a non-NULL `technique_section_id` and survive a subsequent resync.

## Resolution (2026-06-23) — CLOSED
