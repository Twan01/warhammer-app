<objective>
Build the detach data-layer engine — the inverse of the Phase 143 apply / Phase 144 resync flows. A single `detachTechniqueInstance(db, instanceId)` function bakes each technique-owned step's resolved slot-fill colour into `recipe_steps.paint_id`, NULLs the FK link columns, and deletes the instance row (CASCADE removes its slot maps). `recipe_step.id` values are NEVER recreated, so `unit_recipe_step_progress` (keyed by `recipe_step_id`, the v0.2.13 / FND-03 invariant) survives untouched. A second function `detachAllAndDeleteTechnique(techniqueId)` runs the detach for every live instance on one shared db handle, then deletes the technique — preserving all recipe content.

Guard-first discipline (mirroring Phases 143/144): the data-layer test is written FIRST and proves the invariants before the implementation exists.

Purpose: This engine is the gate for the entire phase. SAFE-02 (detach correctness) and SAFE-03 (auto-detach-then-delete) both depend on it. The UI plans (02, 03) call into these functions.
Output: `tests/data-layer/detach-technique.test.ts`, `src/db/queries/recipeTechniqueDetach.ts`.
</objective>

Slot-map SQL for detach context (build map BEFORE any DELETE):
```
SELECT rs.id AS recipe_step_id, sm.paint_id
FROM recipe_steps rs
INNER JOIN recipe_sections sec ON rs.section_id = sec.id
INNER JOIN technique_steps ts ON rs.technique_step_id = ts.id
LEFT JOIN recipe_technique_slot_maps sm
  ON sm.instance_id = sec.technique_instance_id
 AND sm.slot_id = ts.colour_slot_id
WHERE sec.technique_instance_id = $1
  AND rs.technique_step_id IS NOT NULL
```
