    In lib.rs, add the following components. Place new structs near existing BulkSyncPayload (around line 444). Place the new command function near bulk_sync_rules (around line 792). Place the inner helper function just before it.

    1. Define `UnitDatabasePayload` struct with `#[derive(serde::Deserialize)]`:
       Fields: version (String), built_at (String), game_system (Option of String), faction_count (Option of u32), unit_count (Option of u32), factions (Vec of JsRow), units (Vec of JsRow), models (Vec of JsRow), weapons (Vec of JsRow), abilities (Vec of JsRow), keywords (Vec of JsRow), points (Vec of JsRow), composition (Vec of JsRow).

    2. Define `UdbImportResult` struct with `#[derive(serde::Serialize, Debug)]`:
       Fields: factions (u64), units (u64), models (u64), weapons (u64), abilities (u64), keywords (u64), points (u64), composition (u64).

    3. Create `async fn import_unit_database_inner(app: &tauri::AppHandle) -> Result<UdbImportResult, String>`:
       This is the core import logic, callable from both the setup hook and the Tauri command.

       a. Resolve hobbyforge.db path: `app.path().app_data_dir()` then join "hobbyforge.db". Build db_url as `sqlite:{path}`.

       b. Resolve JSON resource: `app.path().resource_dir()` then join "data/unit_database.json". Read via std::fs::read_to_string. Deserialize via serde_json::from_str into UnitDatabasePayload. Per D-07, the JSON ships as a Tauri resource.

       c. Open direct sqlx connection (per D-11, same pattern as bulk_sync_rules lines 497-504): SqliteConnectOptions with create_if_missing(false), journal_mode Wal, busy_timeout 30 seconds.

       d. Check udb_meta version: query `SELECT version FROM udb_meta WHERE id=1`. If the row exists and version matches payload.version, return early with a zero-count UdbImportResult (already up to date). Per D-06.

       e. Set PRAGMA foreign_keys = OFF on the connection.

       f. Begin transaction via conn.begin().

       g. DELETE all udb_* tables in order: udb_search, udb_unit_keywords, udb_unit_points, udb_unit_composition, udb_unit_abilities, udb_unit_weapons, udb_unit_models, udb_units, udb_factions, udb_meta. Use the same `for table in [...]` loop pattern as bulk_sync_rules.

       h. INSERT loops — for each array in the payload, iterate and insert using positional `?` binds. Reuse existing `str_val` and `i64_val` helper functions (already defined in the file). Count rows_affected for each table.

       INSERT INTO udb_factions (id, name, short_name) — bind id, name, short_name from each JsRow.
       INSERT INTO udb_units (id, faction_id, name, role, base_points, damaged_w, damaged_desc) — bind all fields.
       INSERT INTO udb_unit_models (unit_id, line_order, name, M, T, Sv, inv_sv, W, Ld, OC) — bind all fields.
       INSERT INTO udb_unit_weapons (unit_id, weapon_group, line_order, name, category, range, attacks, skill, strength, ap, damage, keywords) — bind all fields.
       INSERT INTO udb_unit_abilities (unit_id, line_order, name, description, ability_type) — bind all fields.
       INSERT INTO udb_unit_keywords (unit_id, keyword, is_faction) — bind all fields.
       INSERT INTO udb_unit_points (unit_id, model_count, points) — bind all fields.
       INSERT INTO udb_unit_composition (unit_id, min_models, max_models, notes) — bind all fields.

       i. INSERT INTO udb_meta (id, version, built_at, game_system, unit_count, faction_count) VALUES (1, ?, ?, ?, ?, ?) — bind from payload metadata.

       j. Rebuild FTS5 index inside the transaction per D-08:
       DELETE FROM udb_search;
       INSERT INTO udb_search(unit_id, name, faction_name, keywords) SELECT u.id, u.name, f.name, COALESCE(GROUP_CONCAT(k.keyword, ' '), '') FROM udb_units u JOIN udb_factions f ON f.id = u.faction_id LEFT JOIN udb_unit_keywords k ON k.unit_id = u.id GROUP BY u.id;

       k. Commit the transaction.

       l. Per D-12, run PRAGMA wal_checkpoint(TRUNCATE) after commit, before returning. This prevents stale WAL reads by the tauri-plugin-sql pool.

       m. Return the UdbImportResult with counts.

    4. Create `#[tauri::command] async fn import_unit_database(app: tauri::AppHandle) -> Result<UdbImportResult, String>`:
       Delegates to import_unit_database_inner(&app).

    5. Update the .setup() closure in run() — per D-06, add a spawned async task after the existing app_data_dir creation:
       Clone app.handle(), spawn via tauri::async_runtime::spawn. Inside the async block, call import_unit_database_inner. Log success with println!("[hobbyforge] udb import: {result:?}") or error with eprintln!("[hobbyforge] udb import failed: {e}").

    6. Register import_unit_database in the tauri::generate_handler![] macro (add after write_bytes_to_path).

    7. Update get_schema_version() — no change needed since it already returns get_migrations().len() which now includes migration 38.

    In tauri.conf.json, add a `resources` field inside the `bundle` object (after `createUpdaterArtifacts`):
    "resources": { "data/unit_database.json": "data/unit_database.json" }

    Use all `.map_err(|e| format!("context: {e}"))` error strings following the existing pattern — every .map_err includes the operation name and key values for diagnosability.

| Boundary | Description |
|----------|-------------|
| JSON resource file → Rust import | Bundled file read by Rust; not user input but could be malformed if build script has bugs |
| Rust import → SQLite | Bulk INSERT into hobbyforge.db; transaction ensures atomicity |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-103-06 | Tampering | unit_database.json in bundle | accept | File is checked into git; serde_json::from_str fails loudly on malformed JSON |
| T-103-07 | Denial of Service | Import during setup hook | mitigate | Import spawned as async task — does not block window creation; errors logged but do not crash the app |
| T-103-08 | Denial of Service | WAL stale reads after import | mitigate | PRAGMA wal_checkpoint(TRUNCATE) after commit per D-12 — documented fix for recurring incident |
| T-103-09 | Tampering | Duplicate rows on re-import | mitigate | Full DELETE-then-INSERT inside single transaction; FK OFF during delete pass ensures clean slate |
