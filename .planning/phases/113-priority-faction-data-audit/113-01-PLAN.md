  <action>
    Create scripts/audit-faction.ts — a Node.js script invoked as:
      node --experimental-strip-types scripts/audit-faction.ts SM
      node --experimental-strip-types scripts/audit-faction.ts NEC
      node --experimental-strip-types scripts/audit-faction.ts DG

    The script accepts a single CLI argument: faction_id (SM, NEC, or DG).

    **Data loading:**
    - Read unit_database.json (from src-tauri/data/) into memory per UnitDatabaseJson shape
    - Read coverage-report.json (from scripts/data/) for unmatched_names per faction
    - Read the 5 Wahapedia CSV files using readCsvFile from scripts/lib/bsdata.ts:
      Datasheets.csv, Datasheets_models.csv, Datasheets_wargear.csv, Datasheets_abilities.csv, Datasheets_keywords.csv
    - Import readCsvFile from ./lib/bsdata.ts (need DOMParser polyfill first, same pattern as build-unit-db.ts)

    **Per D-06 — Matched unit audit (field-by-field comparison):**
    Filter unit_database.json units by faction_id. For each matched unit (has data in DB), find the corresponding CSV row by datasheet_id and compare:

    1. role: DB unit.role vs Datasheets.csv row["role"]
    2. Stats: For each model in DB models[], find CSV models row by (datasheet_id + line). Compare M, T, Sv, inv_sv, W, Ld, OC field by field.
    3. Weapons: For each weapon in DB weapons[], find CSV wargear row by (datasheet_id + line + line_in_wargear or just datasheet_id + name). Compare:
       - category: DB value vs CSV row["type"] (lowercase "type", NOT "wargear_role")
       - range: DB value vs CSV row["range"] (lowercase — this is the known bug; DB will have "" while CSV has the real value)
       - attacks: DB vs CSV row["A"]
       - skill: DB vs CSV row["BS_WS"]
       - strength: DB vs CSV row["S"]
       - ap: DB vs CSV row["AP"]
       - damage: DB vs CSV row["D"]
       - keywords: DB value vs CSV row["description"] (this is the other known bug; DB will have "" while CSV has the real value)
    4. Abilities: For each ability row, match by (datasheet_id + line). Compare name, description, ability_type (CSV column is "type"). Per Pitfall 2, skip empty-name abilities where ability_type is "Core" or "Faction" — these are ability_id references, not errors.
    5. Keywords: For each keyword in DB keywords[], find CSV keyword row by (datasheet_id + keyword). Compare is_faction (CSV column is "is_faction_keyword", value "1" or "0").
    6. Points: Compare DB unit.base_points against BSData-derived points (if available in coverage-report or by re-running matchUnit). Per D-08, also check points tiers if present.

    **Error output format per D-04:**
    Each discrepancy produces an AuditError object:
      { unit_id: string, unit_name: string, field: string, expected: string, actual: string, source: "wahapedia_csv"|"bsdata_xml", severity: "error"|"missing"|"extra" }
    Severity rules: "missing" when DB field is empty but CSV has data. "error" when both have data but differ. "extra" when DB has data but CSV field is empty.

    **Per RESEARCH Pattern 3 — Systematic issues:**
    Before the per-unit loop, detect systematic pipeline bugs. Check if ALL weapons for the faction have empty range (known bug: row["Range"] vs row["range"]). Check if ALL weapons have empty keywords (known bug: row["keywords"] vs row["description"]). These go in a separate systematic_issues array with { field, description, affected_count } — NOT as per-unit errors.

    **Per D-03/D-07 — Unmatched unit classification:**
    Read unmatched_names from coverage-report.json for the target faction. For each unmatched unit name, classify as:
    - "legends": check Datasheets.csv — if the row has legend field == "true" or "1"
    - "forge_world": check Datasheets.csv — if source_id contains "FW" or known Forge World patterns (Fire Raptor, Mastodon, Spartan, Leviathan, Deredeo, Contemptor Dreadnought variant names, Thunderhawk, etc.)
    - "missing_alias": unit exists in Datasheets.csv for this faction (has a row) but BSData uses a different name — heuristic: if the CSV row exists and has no legend/FW markers
    - "genuinely_missing": no matching CSV row found at all (or is a cross-faction unit per Pitfall 5)
    Each gets { unit_name, faction_id, category, evidence: string }.

    **Report generation per D-04/D-05:**
    Build a FactionAuditReport object with:
    - faction_id, faction_name, audited_at (ISO timestamp)
    - systematic_issues array
    - unit_errors array (AuditError[])
    - unmatched_classifications array
    - translation_gaps: { units_missing: number, weapons_missing: number, abilities_missing: number } — count how many matched units lack name_fr, how many weapons lack name_fr, how many abilities lack name_fr
    - summary: { total_matched, total_unmatched, total_errors, errors_by_field (Record of field to count), errors_by_severity }

    Write JSON report to .planning/phases/113-priority-faction-data-audit/reports/{faction_id_lower}-audit.json
    Write markdown summary to .planning/phases/113-priority-faction-data-audit/reports/{faction_id_lower}-audit.md

    The markdown summary (per D-05) should include:
    - Header with faction name, audit date, matched/unmatched counts
    - Systematic Issues table (field, description, affected count)
    - Error Summary table (errors by field, by severity)
    - Top 20 per-unit errors (sorted by unit_name) as a sample
    - Unmatched Unit Classification table (unit name, category, evidence)
    - French Translation Gaps section (counts of missing unit/weapon/ability translations)

    **File organization:** Use same import/path patterns as build-unit-db.ts. Import DOMParser polyfill at top. Use __dirname + join for paths. Ensure reports/ directory is created with mkdirSync recursive.
