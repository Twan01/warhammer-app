<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| fork PR contributor -> CI runner | Untrusted PR code executes in CI on `pull_request` event |
| third-party GitHub Actions -> workflow runtime | External action code runs with workflow permissions |
| ci.yml (callee) -> caller workflows | A workflow_call exposes ci.yml to whatever the caller passes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-131-01 | Information Disclosure | ci.yml on `pull_request` | mitigate | Use `pull_request` (NOT `pull_request_target`); fork PRs run without repo secrets by default. ci.yml declares no `secrets:` and uses none, so even when called there is nothing to leak. Acceptance: ci.yml does NOT contain `secrets: inherit` or `TAURI_SIGNING_PRIVATE_KEY`. |
| T-131-02 | Tampering | third-party actions (checkout/pnpm/node/rust-cache/dtolnay) | accept | Actions pinned to major version tags (@v4/@v2) matching existing release.yml policy; `dtolnay/rust-toolchain@master` is the documented exception required to read the `toolchain:` input (a numeric pin via @rev is not supported by that action). Risk accepted — consistent with the already-trusted release.yml supply chain. |
| T-131-03 | Elevation of Privilege | ci.yml job permissions | mitigate | The test job needs no write scopes; ci.yml declares no `permissions:` block, so it runs with the repo default (read) — it cannot publish, tag, or write releases. Acceptance: ci.yml contains no `contents: write`. |
| T-131-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages are installed by this phase (CI-config only — confirmed by RESEARCH "Package Legitimacy Audit: not applicable"). `pnpm install` restores the existing pinned lockfile; `cargo` restores the existing Cargo.lock (v4). No legitimacy checkpoint required. |
</threat_model>
