# v0.5.0: Code Review Report

**Reviewed:** 2026-06-11
**Depth:** standard
**Files Reviewed:** 35
**Status:** issues_found

## Summary

The v0.5.0 Settings & Preferences milestone is well-structured overall. The key-value app_settings table, preference hooks, and settings UI components follow established project patterns. However, two critical issues were found: (1) the preferences import pipeline has no key allowlist, allowing arbitrary key injection into the settings table, and (2) the UnitDetailSheet silently drops three props from its parent, breaking datasheet conflict resolution. Five warnings cover missing input sanitization, stale React state, and unused prop interface members.

## Critical Issues

### CR-01: Preferences import accepts arbitrary keys without allowlist

**File:** `src/features/settings/DataManagementTab.tsx:89-93`
**Issue:** The `handleImport` function iterates over all entries from a user-provided JSON file and writes any key-value pair where the value is a string directly into `app_settings` via `upsertAppSetting`. There is no allowlist of valid setting keys. A crafted preferences file could inject arbitrary keys that the app never intended to store -- or worse, overwrite keys that other subsystems rely on with malicious values. For example, injecting `pipeline_labels` with a value containing `<script>` tags that later get rendered, or injecting extremely long values that degrade UI.

While this is a desktop app (not web-facing), the attack surface is any JSON file the user opens. Since the app trusts `pipeline_labels` and `default_checklist` values as JSON that gets parsed and rendered, a malicious file could inject values that cause parse errors or unexpected behavior throughout the app.

**Fix:** Add a key allowlist and optionally validate value shapes:
```typescript
const ALLOWED_SETTINGS_KEYS = new Set([
  "locale",
  "currency",
  "default_faction_id",
  "army_readiness_target",
  "pipeline_labels",
  "default_checklist",
  "default_mission_format",
]);

for (const [key, value] of Object.entries(settings)) {
  if (typeof value === "string" && ALLOWED_SETTINGS_KEYS.has(key)) {
    await upsertAppSetting(key, value);
    count++;
  }
}
```

### CR-02: UnitDetailSheet silently drops datasheet conflict props

**File:** `src/features/units/UnitDetailSheet.tsx:50`
**Issue:** The component interface (lines 38-40) declares three optional props: `onDatasheetConflict`, `pendingImportResolution`, and `onClearImportResolution`. However, the function signature on line 50 only destructures `{ open, unit, onClose, onEdit, onDelete, onPhotoClick }` -- the three datasheet conflict props are silently ignored. `CollectionPage.tsx` (lines 270-272) passes all three props, but they have no effect. This means the datasheet import conflict resolution flow is broken: when a PlaybookTab raises a conflict, the callback never fires and the user cannot resolve the conflict.

**Fix:** Either destructure and wire the props through to the PlaybookTab child:
```typescript
export function UnitDetailSheet({
  open, unit, onClose, onEdit, onDelete, onPhotoClick,
  onDatasheetConflict, pendingImportResolution, onClearImportResolution,
}: UnitDetailSheetProps) {
```
Or, if these props were intentionally removed from the flow, remove them from both the interface and the caller to avoid dead code.

## Warnings

### WR-01: PipelineLabelsEditor uses uncontrolled inputs with stale `key` prop

**File:** `src/features/settings/PipelineLabelsEditor.tsx:59`
**Issue:** The Input component uses `key={currentLabel}` to force re-mount when the label changes. However, `currentLabel` is derived from `parsed[bucket] ?? bucket`. If the user types a value that happens to match the bucket name (e.g., clearing a custom label back to "Assembly"), the key stays the same and React will not re-render the input, leaving it showing the old value. More importantly, if two different buckets end up with the same custom label, their inputs share a key and React will confuse them.

**Fix:** Use a stable unique key per bucket instead:
```typescript
<Input
  key={`${bucket}-${currentLabel}`}
  defaultValue={currentLabel}
  ...
/>
```

### WR-02: ReadinessTargetSetting allows float values via parseInt edge case

**File:** `src/features/settings/ReadinessTargetSetting.tsx:28-34`
**Issue:** The `handleBlur` function uses `parseInt(customValue, 10)` which will parse "1500.7" as 1500, silently truncating. However, `Number.isFinite(parsed)` passes for the truncated value. The `<Input type="number">` allows decimal input (e.g., "1500.5") which gets truncated to an integer without user feedback. While not a crash bug, the silent truncation violates the principle of least surprise.

**Fix:** Use `Number(customValue)` and check `Number.isInteger()`:
```typescript
const parsed = Number(customValue);
if (!Number.isInteger(parsed) || parsed < 1 || parsed > 99999) {
  setCustomValue("");
  return;
}
```

### WR-03: ActiveFactionContext boot effect may fire multiple times

**File:** `src/context/ActiveFactionContext.tsx:57-68`
**Issue:** The cold-start effect that reads `default_faction_id` from `settings` has `[activeFactionId, settings]` as dependencies. When `settings` loads (goes from undefined to the map), the effect runs. But if `activeFactionId` was already null and `settings` has a `default_faction_id`, the effect sets `activeFactionId` via `setActiveFactionId`, which triggers a re-render. The dependency array includes `activeFactionId`, so the effect runs again -- but now `activeFactionId !== null` so the early return prevents a loop. This is correct but fragile: if the guard on line 61 were ever removed or weakened, the effect would loop.

**Fix:** Use a ref to track whether the boot migration has already been attempted:
```typescript
const bootAttempted = useRef(false);
useEffect(() => {
  if (bootAttempted.current || activeFactionId !== null) return;
  bootAttempted.current = true;
  // ... rest of effect
}, [activeFactionId, settings]);
```

### WR-04: BattleLogSheet form.reset missing `form` in useEffect dependency array

**File:** `src/features/battle-log/BattleLogSheet.tsx:145-147`
**Issue:** The `useEffect` calls `form.reset(...)` but `form` is not in the dependency array. While `form` from `useForm` is typically a stable reference and this works in practice, the exhaustive-deps rule would flag this. If a future refactor causes `form` to change identity, the effect would use a stale reference.

**Fix:** Add `form` to the dependency array:
```typescript
useEffect(() => {
  form.reset(buildDefaultValues(log, { ...prefill, mission: missionDefault || prefill?.mission || "" }));
}, [form, log, prefill, missionDefault]);
```

### WR-05: GameDayPage async effect lacks error handling for getDefaultChecklist

**File:** `src/features/game-day/GameDayPage.tsx:37-38`
**Issue:** `getDefaultChecklist()` is an async DB call that can reject (e.g., if the DB connection fails). The `.then()` chain has no `.catch()` handler, so a rejected promise becomes an unhandled promise rejection, which could crash the app or produce confusing console errors.

**Fix:** Add error handling:
```typescript
getDefaultChecklist()
  .then((items) => {
    if (!cancelled) {
      useGameDayStore.getState().setDefaultChecklist(listId, items);
    }
  })
  .catch(() => {
    // Fall back to default checklist — store already has defaults
  });
```

## Info

### IN-01: Duplicate locale validation logic across three files

**File:** `src/stores/localeStore.ts:21`, `src/components/common/LocaleToggle.tsx:15`, `src/features/settings/LanguageSetting.tsx:15`
**Issue:** The pattern `raw === "en" || raw === "fr" ? raw : "en"` for locale validation is duplicated in three places. `localeStore.ts` already exports `useLocale()` which does this validation. `LocaleToggle.tsx` duplicates the logic inline instead of using `useLocale()`.

**Fix:** Have `LocaleToggle.tsx` use `useLocale()` from `@/stores/localeStore` instead of re-implementing the validation.

### IN-02: UnitDetailSheet interface has unused optional props

**File:** `src/features/units/UnitDetailSheet.tsx:38-40`
**Issue:** Related to CR-02 -- even after fixing the destructuring, three optional props in the interface (`onDatasheetConflict`, `pendingImportResolution`, `onClearImportResolution`) use inline `import()` type syntax which makes the interface harder to read. If these props are intentionally unused, they should be removed from the interface entirely. If they are needed, the types should be imported at the top of the file.

**Fix:** Import the types at the top level:
```typescript
import type { DatasheetImportPayload, DatasheetImportResolution } from "@/types/datasheet";
```
