# v0.5.0 Full Code Review Report

**Reviewed:** 2026-06-11T14:00:00Z
**Depth:** standard
**Files Reviewed:** 38
**Status:** issues_found

## Summary

The v0.5.0 milestone (Settings & Preferences) is well-structured overall. The app_settings key-value store design is clean, the migration is safe, and the UI components follow established patterns. However, there are two critical issues (a race condition in boot-time default faction, and missing validation on preference import), plus several warnings around stale state, unguarded JSON parsing, and missing query invalidation.

## Critical Issues

### CR-01: ActiveFactionContext boot effect fires only once -- misses late-arriving settings

**File:** `src/context/ActiveFactionContext.tsx:58-68`
**Issue:** The `bootAttempted` ref is set to `true` on the first run of the effect. If `settings` is still `undefined` on that first run (which is the common case -- React Query fetch is async), the boot path exits at `if (!defaultId || defaultId === "")`, sets `bootAttempted.current = true`, and never re-attempts. The user's configured `default_faction_id` is silently ignored on every app start.

The dependency array includes `settings`, so the effect *re-runs* when settings arrive, but the guard `if (bootAttempted.current) return` immediately exits.

**Fix:**
```tsx
const bootAttempted = useRef(false);
useEffect(() => {
  if (bootAttempted.current || activeFactionId !== null) return;
  // Only mark boot attempted when settings have actually loaded
  if (!settings) return; // settings not yet loaded -- wait
  bootAttempted.current = true;
  const defaultId = settings["default_faction_id"];
  if (!defaultId || defaultId === "") return;
  const parsed = Number(defaultId);
  if (Number.isFinite(parsed) && parsed > 0) {
    setActiveFactionId(parsed);
  }
}, [activeFactionId, settings]);
```

### CR-02: Preference import writes arbitrary keys when value is not a string type but JSON coerces

**File:** `src/features/settings/DataManagementTab.tsx:99-103`
**Issue:** The import loop checks `typeof value === "string"` which correctly rejects non-string values. However, the `ALLOWED_IMPORT_KEYS` allowlist does not include length/content validation on the *value* for structured keys like `default_checklist` and `pipeline_labels`. A maliciously crafted (or corrupted) import file could write arbitrarily large strings or malformed JSON into these keys, which are later parsed with `JSON.parse` in multiple consumer components (PipelineLabelsEditor, ChecklistDefaultsEditor, gameDayStore). While each parse site has try/catch, a multi-megabyte string could cause UI hangs since `JSON.parse` is synchronous and blocks the main thread.

More importantly, a crafted `default_faction_id` value like `"0; DROP TABLE"` is safely handled (it goes through `Number()` parse), but `locale` accepts any string -- a value other than `"en"` or `"fr"` would be written and the `useLocale()` hook would fall back to `"en"`, but the locale toggle and LanguageSetting UI would show neither button as active (visual inconsistency until next explicit change).

**Fix:** Add value-level validation per key during import:
```tsx
function isValidImportValue(key: string, value: string): boolean {
  if (key === "locale") return value === "en" || value === "fr";
  if (key === "currency") return (SUPPORTED_CURRENCIES as readonly string[]).includes(value);
  if (key === "army_readiness_target") {
    const n = Number(value);
    return Number.isFinite(n) && n > 0 && n <= 99999;
  }
  // Structured JSON keys: max 100KB guard
  if (value.length > 102400) return false;
  return true;
}
```

## Warnings

### WR-01: BattleLogSheet form reset with object literal in dependency array causes infinite reset loop risk

**File:** `src/features/battle-log/BattleLogSheet.tsx:146`
**Issue:** The `useEffect` dependency array includes `prefill`, which is an object prop. If the parent passes an inline object literal (e.g., `prefill={{ army_list_id: listId, battle_date: todayISO() }}`), a new reference is created on every render, causing the effect to run repeatedly and reset the form. GameDayPage at line 132 does exactly this: `prefill={{ army_list_id: listId, battle_date: todayISO() }}` creates a new object on every render.

While React Hook Form's `reset` with identical values may be a no-op in practice, the `missionDefault` string concatenation in the reset call (`{ ...prefill, mission: missionDefault || prefill?.mission || "" }`) means the spread creates a fresh object every time.

**Fix:** Memoize the prefill in GameDayPage or stabilize the dependency:
```tsx
// In GameDayPage:
const prefill = useMemo(
  () => ({ army_list_id: listId, battle_date: todayISO() }),
  [listId],
);
```

### WR-02: ArmyReadinessCard session override resets on every settings refetch

**File:** `src/hooks/useArmyReadiness.ts:46-63`
**Issue:** `useArmyReadinessTarget` declares `useState<number | null>(null)` for the session override. If the component unmounts and remounts (e.g., tab switch on the dashboard), the session override is lost -- this is by design per D-11. However, the hook is called at the component level, so if `ArmyReadinessCard` is conditionally rendered (which it is -- inside the populated dashboard branch), every navigation away and back resets the target to the persisted default. This is a UX surprise when the user clicks 500 on the dashboard, navigates to Collection, comes back, and sees 2000 again.

**Fix:** Either document this as intentional "session = component mount lifetime" behavior, or move the override into Zustand to survive across navigations within the same app session.

### WR-03: ChecklistDefaultsEditor generates new UUIDs on every settings change

**File:** `src/features/settings/ChecklistDefaultsEditor.tsx:93-114`
**Issue:** The `initialItems` useMemo generates `crypto.randomUUID()` IDs on every recalculation. Since `saveItems` writes back to app_settings, which invalidates the `APP_SETTINGS_KEY` query, the `settings["default_checklist"]` dependency changes, triggering a new `initialItems` memo, which generates new UUIDs, which causes `setItems(initialItems)` via the useEffect at line 119-121. This creates a full re-render of all SortableContext items on every save. While not a bug per se, it means drag handles lose focus and any in-progress interaction is interrupted.

**Fix:** Derive IDs deterministically from item index/text, or suppress the useEffect when the save originated from local state (use a ref flag).

### WR-04: stageLabel getBucketLabel parses JSON on every render for every bucket

**File:** `src/lib/stageLabel.ts:26-38`
**Issue:** `getBucketLabel` calls `JSON.parse(raw)` every time it is invoked. In `HobbyPipeline`, it is called once per bucket (5 times) on every render. While the overhead is small, the `settings` object reference changes on every React Query refetch, causing re-computation even when the value hasn't changed.

**Fix:** Parse once and cache, or move the parsing into the component's useMemo:
```tsx
const labels = useMemo(() => {
  const raw = settings["pipeline_labels"];
  if (!raw) return {};
  try { return JSON.parse(raw) as Record<string, string>; }
  catch { return {}; }
}, [settings["pipeline_labels"]]);
```

### WR-05: LOCALE_QUERY_KEYS missing "udb-search" key

**File:** `src/lib/localeQueryKeys.ts:8-16`
**Issue:** The `LOCALE_QUERY_KEYS` array does not include `"udb-search"`. The FTS5 search index (`udb_search`) contains `name_fr` and `keyword_fr` data. When the user switches locale, search results that matched French terms would show stale results until the query naturally refetches. The `useUdbSearch` hook in `useUnitDatabase.ts` (line 88-95) uses `UDB_SEARCH_KEY` which does not include locale in the key, meaning locale switches never invalidate search results.

**Fix:** Either add `"udb-search"` to `LOCALE_QUERY_KEYS`, or include `locale` in `UDB_SEARCH_KEY`:
```ts
export const UDB_SEARCH_KEY = (query: string, locale: Locale) =>
  ["udb-search", query, locale] as const;
```

## Info

### IN-01: Double useAppSettings calls in SettingsPage + child sections

**File:** `src/app/settings/page.tsx:10` and `src/features/settings/GeneralPreferencesSection.tsx:9` and `src/features/settings/HobbyDefaultsSection.tsx:8`
**Issue:** `SettingsPage` calls `useAppSettings()` for loading/error state, then `GeneralPreferencesSection` and `HobbyDefaultsSection` each call it again independently. With React Query's deduplication this results in only one fetch, but three separate subscriptions. The settings could be passed as props from the parent to avoid redundant subscriptions.

**Fix:** Pass `settings` as a prop from SettingsPage to child sections, or accept the current pattern as idiomatic React Query usage (minimal overhead).

### IN-02: PipelineLabelsEditor calls parseLabels() twice per render

**File:** `src/features/settings/PipelineLabelsEditor.tsx:14-22,39`
**Issue:** `parseLabels()` is called at line 39 to build `parsed`, and again inside `handleBlur` at line 27. The render-time call is not memoized. Minor inefficiency.

**Fix:** Wrap `parseLabels()` result in `useMemo`.

### IN-03: DataManagementTab uses unused navigate import in export/import flows

This is correct, but the `navigate` variable name and its placement alongside the export/import state variables may suggest it was intended for post-import navigation that was removed.

**Fix:** No action needed -- the import is used. Noting for completeness.
